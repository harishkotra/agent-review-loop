Release Readiness Review — checkout-service v2.4

Release manager briefing for the on-call team · Target cut: Thu 14:00 UTC · Owner: R. Mehta · Reviewers: on-call primary, payments lead, SRE lead

1. Summary

checkout-service v2.4 is a low-risk release: it changes how we retry calls to the card vault and adds an idempotency key to the capture path. No public API contract changes, no schema changes that require a down-migration, and no new infrastructure. I am recommending we proceed with the Thursday cut, with one caveat — the eu-west card vault incident (INC-4471) is still open and shares a failure domain with the retry change.

If the on-call primary disagrees with that assessment, the correct action is to block the cut, not to request a delay of the release window. A blocked cut costs us one sprint slot; a bad cut during an open incident costs us the incident.

2. Scope of change

The release contains 14 merged pull requests. The two that matter are the vault retry policy (exponential backoff, 3 attempts, 250 ms base, full jitter) and the capture idempotency key, which is now generated client-side and persisted in Redis with a 24-hour TTL. The remaining twelve are dependency bumps, log-field renames, and test-only changes.

The retry change increases worst-case checkout latency by roughly 1.75 s when the vault is degraded, because three attempts at 250/500/1000 ms plus jitter stack on top of the existing 2 s client timeout. I believe this is acceptable because it only fires on vault errors, but it is the single claim in this document most worth challenging.

3. Error budget status

Our availability SLO for the checkout API is 99.95% over a rolling 30-day window, which gives us 21.6 minutes of allowed unavailability. As of this morning we have consumed 8.1 minutes, leaving 62.5% of the budget. That is a comfortable position, but it is not the number I would use to justify a risky release.

Two of the last seven days account for 5.4 of the 8.1 consumed minutes, and both were vault-related. The budget is healthy; the burn pattern is not.

4. Rollback plan

Rollback is a single command, deploy rollback checkout-service --to v2.3.7, and takes about 4 minutes end to end based on the last two rehearsals. Both new behaviours sit behind feature flags, so the faster path for a partial problem is to disable checkout.vault_retry_v2 and checkout.capture_idem in LaunchDarkly, which propagates in under 30 seconds without a deploy.

There is no down-migration to run. The idempotency key is stored in Redis, not Postgres, and the Redis entries expire on their own within 24 hours; a rollback leaves orphaned keys that v2.3.7 simply ignores. I want the on-call primary to confirm they are comfortable with that claim before we cut.

5. Open incidents

INC-4471 open · sev2 — elevated 5xx from the card vault in eu-west, ongoing for 6 days, root cause not yet identified. It is intermittent and currently affects roughly 0.4% of card authorisations in that region. This is the main reason a reviewer might reasonably block the release.

INC-4488 open · sev3 — duplicate webhook deliveries to three merchant endpoints, observed since Monday. The cause is a known consumer-side dedupe gap, not a checkout-service defect, and it is unrelated to v2.4. I do not consider it a release blocker, but I am flagging it because it will add noise to the on-call rotation during the release window.

6. Monitoring gaps

We have three known gaps that matter for this specific release. First, there is no alert on vault timeout rate — we only alert on the resulting 5xx, which means a retry storm could burn budget for several minutes before anyone is paged. Second, there is no dashboard for idempotency-key collision rate, so if the new capture key is generated incorrectly we would see duplicate captures in merchant reports rather than in our own telemetry.

Third, distributed traces are sampled at 1%, which is too sparse to reconstruct a retry sequence during a low-volume incident. I am proposing we temporarily raise sampling to 10% for the 48 hours after the cut. That is a change to production config, so it needs the SRE lead's explicit approval rather than mine.
